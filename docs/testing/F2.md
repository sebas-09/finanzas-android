# Verificación F2

Alcance: normalización, adaptadores preliminares, persistencia cifrada de candidatos y decisiones de revisión. Los efectos contables, la conciliación y la gestión completa de cuentas corresponden a F3. Ningún banco se declara validado en teléfono físico.

## Casos automatizados

`FinancialParsersTest` cubre 18 casos JVM: centavos exactos y límites de Long, miles inequívocos, signos/desbordamiento/agrupación ambigua, Pichincha entrada/salida, Guayaquil, Produbanco con zona y fechas inválidas/ambiguas/futuras, Deuna pago/recarga, Outlook opt-in sin banco ni Spotify inventados, comercio explícito minimizado, importes contradictorios entre extras, cuenta/fecha sin importe, resúmenes/truncamiento, seguridad/promociones/fallos/moneda extranjera, PeiGo desactivado y extras repetidos. La regresión adicional impide aceptar prefijos de tokens como `$1e3`, números agrupados con espacios/saltos, signos y sufijos alfabéticos; una vista inválida impide elegir silenciosamente el importe válido de otra vista. CA-02–CA-05 se verifican con fixtures sintéticos derivados del spec.

`F2MigrationTest` verifica migración SQLCipher 2→3 con una observación F1 real del esquema exportado, ausencia de datos inventados, integridad de claves foráneas y supervivencia de candidato/cola al cerrar y reabrir. Drenar dos veces y repetir el evento no duplica la observación ni crea transacciones. Se mantiene la regresión de migración 1→3 y cifrado.

`ReviewFlowTest` verifica rechazo de confirmación incompleta y sentido/clasificación incompatibles, creación de cuenta por alias, guardado de borrador y flujo Compose de edición, confirmación e ignorado. Comprueba que el libro mayor sigue vacío.

`CaptureListenerTest` usa el listener real del sistema y una fuente emisora independiente del APK principal: permiso, sesión, pausa, revocación y publicación. F2 conserva revisiones distintas como candidatos separados para la conciliación de F3. No se declara CA-07 completo hasta implementar conciliación y efectos contables idempotentes en F3.

Se mantienen las pruebas de consentimiento y navegación, y la prueba de reapertura entre procesos con `force-stop`.

## Reproducción

Con JDK 17 y SDK 36:

```powershell
.\gradlew.bat test :app:assembleDebug :app:assembleDebugAndroidTest :core:database:assembleDebugAndroidTest lint --no-daemon --no-parallel --max-workers=1
python tooling/verify-manifest.py debug
.\gradlew.bat :core:database:connectedDebugAndroidTest :app:connectedDebugAndroidTest --no-daemon --no-parallel --max-workers=1
powershell -NoProfile -File tooling/test-process-restart.ps1 -Adb adb -Serial emulator-5554 -SkipBuild
```

Usar emuladores o instalaciones dedicadas: las pruebas del listener conceden/revocan acceso y seleccionan el emisor sintético. El APK principal no solicita permiso para publicar notificaciones; lo solicita únicamente el APK de pruebas. La suite estándar omite `ProcessRestartProbe` porque necesita dos invocaciones separadas; el script lo ejecuta expresamente.

En Windows, ejecutar un emulador a la vez y terminar la compilación antes de probar. No modificar ANDROID_USER_HOME durante la compilación: debe conservarse el firmante debug anterior. La serialización de Gradle evita que ambas variantes escriban el mismo esquema Room simultáneamente.

## Límites de aceptación

La aceptación con notificaciones bancarias reales, rendimiento físico/OEM y TalkBack en teléfono permanecen pendientes. Los fixtures no prueban que un banco emita estos extras en una versión concreta de su aplicación. Las decisiones confirmadas no aparecen en agregados financieros hasta F3. Los registros de F1 sin texto no se vuelven a interpretar.

Los resultados finales están en [results.json](evidence-f2/results.json), junto con los logs, el manifest y la firma verificados. El APK entregado es `0.3.0-f2` (código 3), con el mismo firmante de F1 y SHA-256 `c9bfd9bfa66f9805984c6e5dbbcf407bc9ce16c9c3ab04bbbdd448b9ddad0e13`.

| Verificación | Resultado |
|---|---|
| JVM | 22 aprobadas: 4 de modelo y 18 de parsers |
| App API 29 / API 36 | 4 aprobadas en cada plataforma sobre el APK entregado |
| BD API 29 / API 36 | 8 aprobadas en cada plataforma; 1 probe omitido intencionalmente en la suite estándar |
| Reapertura entre procesos | Escritura y lectura aprobadas en ambas plataformas |
| Compilación, lint y permisos del APK | Aprobados |

Después del último cambio de parsers se repitió la suite de app en ambas plataformas. La base de datos y su APK de pruebas conservaron el código ya aprobado. La entrega comprueba que los logs de cada plataforma son posteriores a la generación de los binarios respectivos.

## Incidente del entorno

Durante la preparación de capturas en API 29, al cambiar ajustes de pantalla apareció un ANR de **System UI**. La suite de app/base de datos y la prueba entre procesos habían terminado con éxito. Se conservó [la captura del incidente](evidence-f2/environment-api29-system-ui-anr.png), se cerró el diálogo del componente del sistema y se reanudó la captura con la configuración de pantalla existente. No se borró la instalación principal ni sus datos. La revisión del formulario en tema claro queda en [screenshots-f2](screenshots-f2/).

El esquema exportado de Room omite `indices` cuando no hay índices; el generador del fixture de migración lo trata como una lista vacía. Las pruebas de migración finales se ejecutan con esa corrección.

También se observó [un ANR de System UI en API 36](evidence-f2/environment-api36-system-ui-anr.png) al preparar los ajustes de pantalla, después de aprobar la suite funcional. Tras recuperar ese componente se obtuvieron capturas en modo oscuro y `font_scale=1.5`: [detalle](screenshots-f2/detail-api36-dark-large.png) y [formulario](screenshots-f2/form-api36-dark-large.png). Son comprobaciones visuales puntuales; la validación completa de accesibilidad y TalkBack permanece en F4/F5. Se restauró la pantalla y se cerraron los emuladores al finalizar.
