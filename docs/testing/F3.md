# Verificación F3

F3 incorpora cuentas, registro financiero atómico, conciliación de observaciones, edición, borrado lógico, devoluciones y deshacer. Los importes se representan en centavos enteros. Los totales incluyen únicamente operaciones contabilizadas vigentes. La cobertura bancaria continúa siendo preliminar.

## Pruebas

Las 41 pruebas JVM cubren modelo (4), parsers (18), reglas contables (14) y coincidencias entre observaciones (5). Verifican compras a crédito, pagos, recargas, transferencias, devoluciones parciales, saldo inicial desconocido, exclusión de pendientes y límites numéricos. Las coincidencias de importe y minuto solo sugieren una relación. La asociación automática exige publicación idéntica o referencia bancaria y contexto compatibles.

`BookStoreTest` cubre nueve recorridos instrumentados. Incluye callbacks repetidos, revisiones distintas, compras legítimas iguales, referencia entre canales y coincidencias múltiples, reclasificación tardía de recarga, pago de tarjeta desde un aviso pendiente, reintentos idempotentes, límites de devoluciones, borrado, edición concurrente y versiones que aumentan incluso después de deshacer. Las pruebas comprueban que deshacer conserva operaciones independientes, decisiones y metadatos de origen posteriores. Los candidatos sintéticos se rechazan al contabilizar.

`F3MigrationTest` parte de una base SQLCipher v3 y verifica la migración a v4, claves foráneas, normalización de tarjeta de débito y conservación de saldo y decisiones F2. Esas decisiones continúan pendientes de contabilización explícita. La clave y los datos sobreviven a la reapertura.

`BookFlowTest` usa el formulario Compose de entrada manual. Selecciona cuenta y gasto, introduce `3,99`, contabiliza 399 centavos y comprueba el saldo de 9601 desde 10000. Deshacer elimina sus efectos y restaura 10000. También se conservan las pruebas de consentimiento, navegación, listener y revisión de F2.

## Reproducir

Con JDK 17 y Android SDK 36, ejecutar desde la raíz del proyecto.

```powershell
.\gradlew.bat test :app:assembleDebug :app:assembleDebugAndroidTest :core:database:assembleDebugAndroidTest lint --no-daemon --no-parallel --max-workers=1
python tooling/verify-manifest.py debug
.\gradlew.bat :core:database:connectedDebugAndroidTest :app:connectedDebugAndroidTest --no-daemon --no-parallel --max-workers=1
.\tooling/test-process-restart.ps1 -Adb adb -Serial emulator-5554 -SkipBuild
```

Usar emuladores o instalaciones de ensayo para las pruebas instrumentadas. El listener de pruebas concede y revoca acceso a una fuente sintética. En Windows se ejecutó un emulador a la vez, con compilación previa y tareas Gradle serializadas.

La sesión de construcción tomó una clave debug predeterminada diferente según el contexto del shell. Se firmaron explícitamente los tres APK con la clave debug original y se verificó el certificado SHA-256 `4c25c60c1f166aa9048df078172f89164251d5b6a15f59b9cdc1f4d23f25f656` antes de instalarlos mediante actualización. La clave permanece fuera del proyecto.

## Revisión visual y límites

Se revisaron los formularios de cuentas y movimiento manual en tema claro en API 29, incluido el desplazamiento hasta sus acciones. Las capturas están en [screenshots-f3](screenshots-f3/). Se corrigió el texto heredado del estado de captura que aún describía la capacidad de F1. Las capturas de formularios preceden a esa corrección de texto compartido.

Después de aprobar las pruebas funcionales apareció un ANR de System UI al abrir la app para capturas. Se guardó [la incidencia](evidence-f3/environment-api29-system-ui-anr.png), se cerró el componente bloqueado y se continuó la revisión. La instalación principal y sus datos se conservaron.

En API 36, el perfil usado en fases anteriores reinició sus servicios del sistema durante dos intentos de arranque. Se creó el perfil adicional `finanzas-f3-api36-clean`, de 720 × 1280, usando la misma imagen Android 16. Tras completar su primer arranque y desactivar Bluetooth se ejecutaron las pruebas. El perfil anterior se conservó. La prueba de migración usa una base cifrada v3 preparada expresamente dentro de la suite.

La validación bancaria física, rendimiento OEM, TalkBack y revisión completa de accesibilidad siguen pendientes. El resumen actual cubre todo el período registrado. El dashboard mensual, filtros, categorías, ciclos de crédito y presupuestos corresponden a F4. PeiGo admite crédito manual y su parser permanece desactivado. El artefacto de esta fase es debug.
